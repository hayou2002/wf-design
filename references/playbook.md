# 设计工作流 · 编排手册

这里只写技能如何组织、阶段如何交接。专项设计方法读取对应技能，不在此复制。

## 名词速查

- **设计契约**：动手前对页面职责、信息层级、关键状态、响应式和共享规则的简短约定。
- **方向样板**：验证视觉与信息方向的最小真实页面，不等于完整产品。
- **页面地图**：记录用户任务、页面关系、关键状态、数据来源和验收场景的清单。
- **垂直切片**：把一条高风险用户任务从界面到数据、交互和测试完整做通的一片能力。
- **切片审查**：计划时划清一片工作，完成后先验收该片，再继续下一片。
- **变更控制**：新意见先判断影响范围，再决定修改、排期或重新确认。

## 进度怎么报

简单任务：一句话包含当前动作、真实状态和下一步。

复杂任务在每阶段开始、等待用户、切片完成和受阻时更新：

```text
当前：3 / 7 · 设计契约
状态：进行中 / 等待你确认 / 待验收 / 已完成 / 受阻 / 已超时
本步目的：先确定页面为什么这样设计，再制作样板
本步产物：设计契约与需要拒绝的模板化做法
下一步：制作关键方向样板
```

使用子 Agent 时，按实际任务列出：任务、目的、Agent、模型、状态、负责产物。拿不到模型或进度证据就写未核实或状态未知，不编造百分比。所有子 Agent 到终态后统一汇报一次，不逐条转发过程。

## 1. 明确任务与分档

```text
真实用户与核心任务：谁在什么场景完成什么
交付终点：设计稿 / 样板 / 可运行页面 / 正式文件 / 展示图
真实内容与数据：来源是什么，哪些是未知
现有约束：品牌、设计体系、技术栈、尺寸、不可改部分
验收方式：用户怎样判断任务完成，需要哪些页面和状态
复杂度：小改 / 简单设计 / 复杂设计
```

只问资料查不到且会改变方向的问题，一次集中 1–3 个并给推荐默认值。小改直接做；复杂设计不能只靠一张样板推断整个项目。

## 2. 核验事实与参考

先查真实项目、设计规范、源码、真实数据和现有组件。需要外部参考时，AI 按具体问题检索并打开最相关的示例，不让用户自己浏览整个库，也不把目录或 JSON 交给用户。

| 类型 | 处理 |
| --- | --- |
| 已核实事实 | 可进入实现契约，注明来源 |
| 设计建议 | 主控或用户确认后采用 |
| 待核实假设 | 明确标记，不交给执行者照抄 |

来源调用方式、费用、许可和止损规则见 [参考资源索引](references-library.md)。大改确认参考意向；已有明确设计体系或用户已选定方向时不停。

## 3. 写设计契约

契约保持一页以内，包含：

1. 页面职责、真实用户与主要操作。
2. 信息层级、布局概念、导航与关键内容。
3. 加载、空、错误、成功、权限或恢复等本次真正需要的状态。
4. 响应式、键盘、焦点与减少动态效果要求。
5. 颜色、字体、间距、圆角等共享变量及项目来源。
6. 与这个业务有关的记忆点，以及不采用的通用模板做法。

先由 oil-ui-pro 组织；全新视觉方向按需读 frontend-design，涉及真实组件与状态时按需读 frontend-ui-engineering。检查设计是否业务相关，而非机械禁止某种颜色、卡片或字体；用户确认的品牌与项目规范优先。

## 4. 做方向样板

网页做一个关键页面，模块做正常状态和一个关键状态，文档做代表性页面，视频做关键分镜或短试片。使用真实或脱敏代表性内容，覆盖长名称、空值和异常等影响布局的情况。

**停点：确认方向样板。** 修改只发生在样板范围；局部调整继续改同一样板，整体方向变化才回到参考与设计契约。

## 5. 走通真实任务（复杂项目）

| 用户任务 | 页面与入口 | 关键状态 | 数据来源与权限 | 验收场景 |
| --- | --- | --- | --- | --- |
| 要完成的实际任务 | 从哪进来、完成后去哪 | 正常 / 空 / 加载 / 失败 / 恢复 | 真实来源、可见范围 | 如何证明完成 |

先用最小技术骨架验证入口、数据、权限、路由和反馈，再选最高风险任务做完整垂直切片。让非专业用户用真实或代表性数据完成一次任务，不只看静态图片。付费、权限和数据可见范围交回开发流程验证，不能只靠前端遮挡。

## 6. 规范与分批制作

从已确认样板提取共享变量、组件、导航和状态规则。已有组件库时沿用，不另建一套；长期项目将确认后的规则写入 `DESIGN.md`，一次性任务不强行创建。

计划时划分切片，每片写清：

```text
目标与负责产物 / 修改范围与共享文件负责人 / 验收标准 / 执行与审查方式
```

实现网页组件时，oil-frontend 主责，frontend-ui-engineering 按需补组件组合、状态分层和可访问性检查。需要界面动效时先用 animate 判断频率与目的；可以得出“不动”的结论。优先项目已有变量、组件和工具，不为动效或检查擅自加依赖。

### 新意见怎么处理

| 情况 | 处理 |
| --- | --- |
| 局部修正 | 进入当前切片 |
| 新页面或新状态 | 加入页面地图，安排当前或下一切片 |
| 整体方向变化 | 暂停受影响部分，重新确认设计契约或小样 |
| 与已确认规则冲突 | 列出影响与推荐选择，请用户确认 |
| 与当前目标无关 | 记入后续候选，不插队 |

记录影响哪些页面、组件、数据和测试，以及需要重新验收什么；未受影响部分不返工。

## 7. 逐片审查与集成验收

每片稳定后先审查该片，再进入下一片。普通切片可由执行者自审；主控核对真实产物、任务目标和必要测试。视觉大改、复杂交互、共享规范和跨片状态需要独立或主控复核。

存在界面动效时，显式调用 review-animations，输出问题位置、修复建议与通过/阻断结论。其未安装的同作者扩展不得假装可用，按已安装文件和当前项目规范复核。

集成验收检查完整任务、跨片一致性、真实画面与最终状态，不重复所有局部审查。交付时分别报告：设计确认、代码实现、测试、真实浏览器或文件验证、生产环境状态；任何一项未做都不冒充另一项。

## 能力与规则怎么增补

1. 先读能力 Skill，提炼它改变的判断、产物或验收点，再决定放在哪个阶段。
2. 同一职责只有一个主用技能，其他按需补充；不把多个相似 Skill 串成重复步骤。
3. 只有少量通用规则值得采用时，写入本手册对应位置；完整且会更新的方法保留引用。
4. 新参考来源只改资源登记与对应适配契约，不重写通用流程。
5. 个人偏好与已验证踩坑写 habits.md；失效、重复或已有技能覆盖的内容及时删除。
